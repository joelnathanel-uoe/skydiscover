One full iteration — step by step

Every iteration of run_discovery() executes the same 7-step sequence. Only one island is active per iteration.

1
UCB selects one island — adaptation.py → select_dimension_ucb(). Balances reward (recent score improvements) vs exploration bonus (grows when island hasn't been visited recently). Only one island runs this iteration.
iter 1 → island 0   (both underexplored, random pick)
iter 2 → island 1   (island 0 just visited, 1 hasn't been)
iter 3 → island 0   (island 0 got a good score, high reward)
iter 4 → island 1   (island 1 falling behind on visits)
iter 15 → migration runs (ring: 0→1→0)
2
Sampling mode drawn from intensity — adaptation.py → get_search_intensity() returns a value [0.15, 0.5] based on G. High G (many recent improvements) → low intensity → mostly exploitation. Low G (stagnating) → high intensity → mostly exploration.
high G → intensity≈0.15 → exploitation 72%, exploration 15%, balanced 13%
low G → intensity≈0.5 → exploitation 35%, exploration 50%, balanced 15%
3
Parent sampled from that island's archive — unified_archive.py → sample_parent(mode). Exploitation: random pick from top 25% by combined_score (or Pareto front if configured). Exploration: roulette-wheel weighted by novelty score. parent.solution is the actual Python code string of the chosen program.
4
LLM call → raw response — controller.py → _call_llm(). Prompt includes: system message (problem description), parent code, EXPLORE_LABEL or EXPLOIT_LABEL, any human feedback, and paradigm guidance if active. LLM returns a raw text string (response) containing explanation + code or diff blocks.
5
Parse child code from response — controller.py → _execute_generation(). If diff mode: scan response for <<<<<<< SEARCH / ======= / >>>>>>> REPLACE blocks and apply them to parent.solution. If no blocks found, fall back to extracting a full ```python``` block. Result is child_solution — the new Python code string.
6
Evaluator scores the child — evaluator.py → evaluate(program_path). Runs child in a subprocess on all benchmark instances. Returns combined_score (and tight_score / loose_score if configured). Score stored in program.metrics.
combined_score = mean over instances of wspt_twt / (wspt_twt + heuristic_twt)
0.5 = matches WSPT baseline   1.0 = zero tardiness
7
Child added to island archive — unified_archive.py → add(program). Elite score computed: fitness_weight × fitness_pct + novelty_weight × novelty_pct + pareto_weight × pareto_pct. If archive full, child competes against its most similar program (deterministic crowding) — higher elite score wins.
8
G signal and UCB updated — adaptation.py → record_evaluation(). If child beat island's best score: G accumulates (intensity drops next iteration → more exploitation). UCB reward for this island updated with globally-normalised delta. Stagnation window updated. → loop back to step 1.
Explore vs Exploit — Two Independent Levels

The same tradeoff appears twice, at different scales

AdaEvolve has explore/exploit logic at two completely separate levels. They are driven by different mechanisms and make different decisions. One decides which island to run. The other decides which program within the island to mutate.

Level 1 — UCB island selection

Exploit: pick the island that has been getting the best score improvements recently (high reward_avg)

Explore: don't neglect an island that hasn't been visited for a while — its UCB bonus grows as √(ln(N) / visits)

Driven by: adaptation.py → select_dimension_ucb()

Level 2 — Parent sampling within island

Exploit: sample from the top 25% by fitness — refine what's already good

Explore: sample weighted by novelty score — mutate something structurally unusual

Driven by: database.py → _sample_from_archive()

They are independent. UCB can be exploiting a productive island while parent sampling is in exploration mode within that island — mutating a novel but weak program rather than the current best. Or vice versa. The two mechanisms don't communicate with each other.

How the sampling mode is chosen — the actual formula

Once an island is selected, search intensity (from the G-signal) determines the probability of each mode:

database.py — mode probability formulalines 556–564
# Formula: exploration=intensity%, exploitation=(1-intensity)*70%, balanced=(1-intensity)*30%
# Example with intensity=0.4: exploration=40%, exploitation=42%, balanced=18%
rand = random.random()
if rand < intensity:
    mode = "exploration"
elif rand < intensity + (1 - intensity) * 0.7:
    mode = "exploitation"
else:
    mode = "balanced"
intensity = 0.15 (low, mature run with many improvements) → exploration = 15% → exploitation = 72% (= 0.85 × 70%) → balanced = 13% intensity = 0.5 (high, early run or stagnating) → exploration = 50% → exploitation = 35% (= 0.50 × 70%) → balanced = 15%

How each mode selects the parent

  • exploitation — sort archive by combined_score, take top 25%, pick one at random. If Pareto objectives configured: sample from the Pareto front weighted by crowding distance instead.
  • exploration — pick randomly, weighted by novelty score. Programs furthest from others in code-space are most likely.
  • balanced — 50/50 coin flip between exploitation and exploration.

The mode is also told to the LLM

The sampling mode isn't just internal bookkeeping — it gets injected into the prompt as a label. These are real strings defined in database.py:

database.py — EXPLORE_LABEL and EXPLOIT_LABELlines 41–85
EXPLORE_LABEL = """
This parent was selected through diversity-driven sampling
to explore different regions of the solution space.
Consider making more substantial structural changes.
"""

EXPLOIT_LABEL = """
This parent was selected through fitness-based sampling
to exploit high-performing solutions.
Consider making targeted refinements to improve performance.
"""
Why tell the LLM? The label nudges the LLM toward bolder changes (exploration) or smaller refinements (exploitation) without hard-coding mutation sizes. The LLM gets the parent code plus this hint and decides how much to change. It's a soft signal, not a constraint.

controller.py The Main Loop

What it does

Owns the top-level run_discovery() loop. Each iteration it checks for paradigm stagnation, samples a parent from the database, builds the LLM prompt (including human feedback and paradigm guidance), calls the LLM, parses the response as a code diff or full rewrite, evaluates the candidate, and hands the result back to the database. All timing, logging, and retry logic lives here too.

controller.py — run_discovery()lines 226–266
async def run_discovery(self, start_iteration, max_iterations, checkpoint_callback):
    total = start_iteration + max_iterations
    self._setup_iteration_stats_logging()  # opens the .jsonl log file
    self._ensure_all_islands_seeded()      # copy seed to any empty islands

    for iteration in range(start_iteration, total):
        if self.shutdown_event.is_set():
            break
        try:
            await self._run_iteration(iteration, checkpoint_callback)
        except Exception as e:
            logger.exception(f"Iteration {iteration} failed: {e}")
        finally:
            # CRITICAL: triggers UCB update and migration check
            self.database.end_iteration(iteration)
Why end_iteration() is in finally: It must run even if the iteration throws an exception. This is what advances the UCB island selection and triggers migration. If it were skipped on failures, one island could get stuck being selected forever.

What is response?

response is the raw text string returned by the LLM — completely unparsed. It includes any explanation the LLM wrote plus the code block or diff blocks. The parsing functions then extract just the code from it.

What the LLM response looks like in diff mode

The LLM might return a mix of explanation and one or more SEARCH/REPLACE blocks. The entire thing is response. extract_diffs() scans it with a regex for the markers and returns just the pairs.

What is parent.solution?

parent.solution is the stored Python code of whichever program was sampled from the archive — not the LLM response from the previous iteration. It could be the best program from iteration 3 still being used as a parent in iteration 47. The diff is applied to that stored code to produce the child's code.

database.py — _sample_pareto_front() — crowding distance weightinglines 677–699
def _sample_pareto_front(self, archive, population):
    # Get all rank-0 programs (the actual Pareto front)
    front_programs = [
        archive.get(pid)
        for pid, rank in archive._pareto_ranks.items()
        if rank == 0
    ]

    if len(front_programs) < 2:
        return self._sample_top(population)  # not enough for Pareto

    # Weight by crowding distance — prefer programs in sparse regions
    # (programs in crowded regions are less unique)
    weights = []
    for p in front_programs:
        cd = archive._crowding_distances.get(p.id, 0.0)
        if cd == float("inf"): cd = 1e6
        weights.append(max(cd, 0.001))

    return random.choices(front_programs, weights=weights, k=1)[0]
Crowding distance weighting means the search preferentially evolves from programs in sparse objective-space regions — heuristics that are unlike their neighbours on the Pareto front. This naturally diversifies the types of heuristics evolved, directly relevant to RQ2 and RQ3.

adaptation.py The Maths — G Signal, Search Intensity, UCB

What it does

Two classes: AdaptiveState (one per island) tracks the accumulated improvement signal G and computes search intensity. MultiDimensionalAdapter manages all islands together and runs UCB selection to decide which island gets the next iteration.

The core insight

Inspired by Adam/AdaGrad — those adapt gradient descent step sizes based on gradient history. AdaEvolve adapts LLM exploration aggressiveness based on improvement history. A productive island should exploit (small edits to refine); a stagnating island should explore (big structural changes).

adaptation.py — AdaptiveState.record_evaluation()lines 84–114
def record_evaluation(self, fitness):
    self.total_evaluations += 1

    if fitness > self.best_score:
        raw_delta = fitness - self.best_score
        normalized_delta = self._normalize_delta(raw_delta)
        self.best_score = fitness
        self.improvement_count += 1

        # G_t = ρ * G_{t-1} + (1 - ρ) * δ²
        # Exponential moving average of squared normalised improvements
        self.accumulated_signal = (
            self.decay * self.accumulated_signal
            + (1 - self.decay) * (normalized_delta ** 2)
        )
        return normalized_delta

    return 0.0  # no improvement — G decays naturally each iteration
adaptation.py — get_search_intensity()lines 152–171
def get_search_intensity(self):
    # intensity = I_min + (I_max - I_min) / (1 + √(G + ε))
    G = self.accumulated_signal

    intensity = self.intensity_min + (
        (self.intensity_max - self.intensity_min) / (1 + math.sqrt(G + self.epsilon))
    )
    return intensity
intensity = I_min + (I_max - I_min) / (1 + √(G + ε)) High G (many recent improvements) → denominator large → intensity → I_min → exploit Low G (no recent improvements) → denominator = 1 → intensity → I_max → explore Default: I_min = 0.15, I_max = 0.5, decay ρ = 0.9
adaptation.py — MultiDimensionalAdapter — TWO normalisation schemeslines 318–371
def record_evaluation(self, dim_idx, fitness):
    local_best_before = self.states[dim_idx].best_score

    # 1. LOCAL normalisation → search intensity (per-island scale)
    local_delta = self.states[dim_idx].record_evaluation(fitness)

    self.dimension_visits[dim_idx] += 1
    self.decayed_visits[dim_idx] = self.decay * self.decayed_visits[dim_idx] + 1.0

    if fitness > local_best_before:
        raw_delta = fitness - local_best_before
        # 2. GLOBAL normalisation → UCB rewards (cross-island fairness)
        global_delta = self._normalize_by_global(raw_delta)

        if fitness > self.global_best_score:
            self.global_best_score = fitness
    else:
        global_delta = 0.0

    # UCB reward uses DECAYED reward + DECAYED visits
    self.dimension_rewards[dim_idx] = (
        self.decay * self.dimension_rewards[dim_idx] + global_delta
    )
    return local_delta
Why two normalisations? Without global normalisation, a weak island making small local gains (e.g. score improving from 0.1 → 0.15, a 50% local gain) would dominate UCB over a strong island making globally valuable improvements (e.g. 0.6 → 0.62, only 3% local). Global normalisation makes cross-island rewards comparable.
adaptation.py — UCB selectionlines 403–463
def select_dimension_ucb(self, total_iterations):
    # Ensure minimum visits first (randomised to avoid always picking island 0)
    underexplored = [i for i in range(n_dims) if self.dimension_visits[i] < self.min_visits]
    if underexplored:
        return random.choice(underexplored)

    best_dim, best_ucb = 0, float("-inf")
    for i in range(n_dims):
        dec_visits = self.decayed_visits[i]
        # recent reward per recent visit (decayed so old wins fade)
        reward_avg = self.dimension_rewards[i] / dec_visits if dec_visits > 0 else 0.0

        # classic UCB exploration bonus (raw visits for correct ln scaling)
        exploration_bonus = self.ucb_exploration * math.sqrt(
            math.log(total_iterations + 1) / self.dimension_visits[i]
        )
        ucb_score = reward_avg + exploration_bonus

        if ucb_score > best_ucb:
            best_ucb = ucb_score
            best_dim = i
    return best_dim
UCB score = reward_avg + C × √(ln(N) / visits) reward_avg = decayed_rewards / decayed_visits ← recent reward per recent visit C = 1.41 (√2, classic UCB constant) N = total iterations across all islands visits = raw visit count for this island Decaying rewards means old breakthroughs fade — islands don't get credit forever.
archive/unified_archive.py Quality-Diversity Archive

What it does

One archive per island. Stores programs and ranks them by a combined elite score (fitness + Pareto + novelty). Uses deterministic crowding for replacement — when a new program is added, it competes against its most similar existing program rather than the worst one. This preserves diversity while still favouring quality.

unified_archive.py — _compute_novelty() — k-NN distancelines 392–414
def _compute_novelty(self, program, all_programs):
    """Novelty = average distance to k nearest neighbours."""
    others = [p for p in all_programs if p.id != program.id]

    if not others:
        return 1.0  # max novelty if alone in archive

    # Distance to every other program in archive
    distances = [self.diversity.distance(program, other) for other in others]
    distances.sort()

    # Average over k nearest — high = program is in sparse code space
    k = min(self.config.k_neighbors, len(distances))
    return sum(distances[:k]) / k
O(n²) cost: novelty is recomputed for every program against every other every time the cache is invalidated. This is why archive_size: 100 is the default — larger archives make this expensive. For FJSP_TWT this is fine since evaluation is the bottleneck, not archive computation.
unified_archive.py — _compute_pareto_ranking() — NSGA-IIlines 420–499
def _compute_pareto_ranking(self, programs):
    """NSGA-II: non-dominated sorting + crowding distance."""
    objectives = self.config.pareto_objectives  # e.g. ["tight_score", "loose_score"]

    # Build objective vectors (flip sign for minimisation objectives)
    obj_vectors = {}
    for p in programs:
        vec = []
        for obj_key in objectives:
            val = p.metrics.get(obj_key, 0.0)
            if not higher_is_better.get(obj_key, True):
                val = -val  # flip so "higher is always better" internally
            vec.append(float(val))
        obj_vectors[p.id] = vec

    # Non-dominated sorting into layers (rank 0 = Pareto front)
    remaining = set(p.id for p in programs)
    rank = 0
    while remaining:
        front = [pid for pid in remaining
                 if not any(self._dominates(obj_vectors[other], obj_vectors[pid])
                            for other in remaining if other != pid)]
        for pid in front:
            pareto_ranks[pid] = rank
        rank += 1

    # Crowding distance within each layer
    for m in range(num_objectives):
        sorted_layer = sorted(layer, key=lambda pid: obj_vectors[pid][m])
        crowding[sorted_layer[0]] = float("inf")   # boundary = max spread
        crowding[sorted_layer[-1]] = float("inf")
        for i in range(1, len(sorted_layer) - 1):
            crowding[sorted_layer[i]] += (
                obj_vectors[sorted_layer[i+1]][m] - obj_vectors[sorted_layer[i-1]][m]
            ) / obj_range
Crowding distance measures how much space surrounds a program in objective space. Programs at the extremes (best on tight, or best on loose) get infinite distance. Programs in densely-clustered regions get low distance. The archive prefers to keep high-crowding programs — this is what maintains diversity across the Pareto front.

Length difference20%Normalised difference in code length. A much longer or shorter program is considered more novel.
Limitation for FJSP_TWT: This is syntactic not semantic novelty. Two programs implementing the same dispatching logic with different variable names would score low distance. Two programs using completely different features (one uses slack, one uses machine load) would score high. It's a reasonable but imperfect proxy for the "design space coverage" you care about in RQ2/RQ3.

Alternative strategies (available but not default)

  • MetricDiversity — uses normalised Euclidean distance across evaluator metrics (e.g. tight_score, loose_score). Two programs with different score profiles are considered different.
  • HybridDiversity — weighted combination of code + metric diversity. Most powerful but requires metric diversity to be meaningful.

Switch via diversity_strategy: "metric" or "hybrid" in config.

paradigm/tracker.py Stagnation Detection

What it does

Maintains a sliding window of binary improvement signals and detects when the search has stagnated. Manages the lifecycle of active paradigms — tracking which one is currently active, how many times each has been used, and archiving completed ones with their outcomes (SUCCESS/FAILED).

def is_paradigm_stagnating(self):
    # Need enough history to make a judgment
    if len(self.improvement_history) < self.window_size:
        return False

    # If we have active paradigms, use them first before generating new ones
    if self.has_active_paradigm():
        return False

    # Stagnating if improvement rate < threshold
    # Default: window=10, threshold=0.12 → fewer than 12% of recent iters improved
    return self.get_improvement_rate() < self.improvement_threshold

This means the generator knows "ATC-style slack rules were tried and succeeded" or "look-ahead approaches were tried and failed" — it learns what directions are worth pursuing.
paradigm/generator.py Breakthrough Idea Generation

What it does

When stagnation is detected, calls the LLM with a meta-prompt: "here is the current best heuristic, its score, and what we've already tried — suggest 3 fundamentally different algorithmic directions to try next." Returns a list of paradigm dicts that get injected into subsequent iteration prompts.

For FJSP_TWT this is where domain knowledge matters. If the initial Stage 1 run stagnates on WSPT variants, paradigm generation might suggest ATC, EDD, or slack-based rules — exactly the design space diversity you want to track in RQ2. Examining which paradigms were generated and whether they succeeded or failed is part of your trajectory analysis.

Max uses and rotation

Each paradigm is used max_paradigm_uses times (default 5) before rotating to the next. With 3 paradigms generated per trigger, that's 15 iterations of paradigm-guided search before the tracker checks stagnation again. If none of the paradigms improved the score, they're all archived as FAILED and the next stagnation check can trigger a new generation with those failures as context.
