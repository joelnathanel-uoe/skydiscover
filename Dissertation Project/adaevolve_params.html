1 — How Scoring Works in AdaEvolve

A single number — combined_score — comes out of the evaluator and then flows into five separate mechanisms inside AdaEvolve, each using it differently. This section traces that journey from evaluation output to search decision.

1.0 — Where the score comes from: the evaluator

Every iteration, after the LLM generates a new heuristic, it is run on all 209 instances inside a subprocess. The evaluator returns a dict of metrics. AdaEvolve only cares about the key named fitness_key (combined_score in Stage 1).

Step 1 — WSPT baseline (pre-computed once at import)

for each of the 209 instances at evaluator startup: schedule = wspt_solve(instance) # priority = weight / proc_time, greedy dispatch WSPT_BASELINES[path] = compute_twt(instance, schedule)

Step 2 — Per-instance score

score_i = wspt_twt_i / (wspt_twt_i + heuristic_twt_i) score_i = 1.0 → heuristic achieves zero tardiness (perfect) score_i = 0.5 → heuristic matches WSPT exactly (baseline) score_i = 0.0 → heuristic TWT much larger than WSPT, or instance timed out / errored

Step 3 — combined_score (fail-any policy)

If ANY instance returns an error or timeout: combined_score = 0.0 (evaluation stops immediately, remaining instances skipped) Otherwise: combined_score = mean(score_i) over all 209 instances

The evaluator also computes validity, eval_time, n_instances, etc., but these are logged only — AdaEvolve's selection mechanisms ignore them completely in Stage 1. The only number that drives all five mechanisms below is combined_score.

1.1 — Mechanism 1: Adaptive signal G → search intensity (within-island explore/exploit)

Each island maintains an accumulated improvement signal G that tracks how productive it has been recently. G drives a per-island search intensity which sets the probability of exploring (try something new) vs exploiting (refine what works).

When G is read and written

READ: at the start of each iteration, during sample() intensity = f(G) → mode drawn → parent selected (uses whatever G was left from the previous iteration — one-iteration lag) WRITE: later in the same iteration, inside add(), after archive admits the program only if new combined_score > island's current best — otherwise G is not touched at all
G does not decay by itself. The EMA formula only fires on an improvement event. If an island stops improving, G sits frozen at its last value indefinitely — it does not drift toward zero with time. This means a previously-productive island keeps a low intensity (exploit-biased) even through a long dry spell. The UCB mechanism is what eventually routes iterations away from it (see §1.2).

δ — the improvement signal fed into G

δ = min( (combined_score − island_best) / (|island_best| + ε), 1.0 ) numerator: how much the new program improved over this island's previous best denominator: the island's own current best → local normalisation, scale-invariant special case: first program on island → island_best = −∞ → δ = 1.0 (capped)

δ is local — each island normalises by its own best, not the global best. This lets each island's intensity adapt to its own scale of progress independently of how other islands are doing.

G update (only fires when combined_score improves island best)

G_t = ρ · G_{t-1} + (1 − ρ) · δ² ρ = decay = 0.9 → exponential moving average, ~10-iteration half-life δ² squares the improvement so larger gains push G up more aggressively no improvement → G unchanged (not decremented, not decayed)

Intensity from G

intensity = I_min + (I_max − I_min) / (1 + √(G + ε)) G → 0 (stagnating) : intensity → I_max = 0.5 (explore aggressively) G → ∞ (productive) : intensity → I_min = 0.15 (exploit more)

Mode draw — once per iteration, for the selected island only

r = random() if r < intensity → mode = "exploration" elif r < intensity + (1 − intensity)·0.7 → mode = "exploitation" else → mode = "balanced" Example — intensity = 0.4: 40% exploration · 42% exploitation · 18% balanced Example — intensity = 0.15 (very productive island): 15% exploration · 72% exploitation · 13% balanced Example — intensity = 0.5 (fully stagnating island): 50% exploration · 35% exploitation · 15% balanced
What each mode does to parent selection:
exploitation — random choice from top-25% by combined_score in the archive
exploration — weighted random by novelty score (k-NN distance); fitness completely ignored
balanced — 50/50 coin-flip between the two

The mode label is also injected into the LLM prompt as a guidance header (EXPLOIT_LABEL / EXPLORE_LABEL) so the model is told whether to refine or rethink.
1.2 — Mechanism 2: UCB rewards → island selection (which island works next)

At the end of each iteration, end_iteration() picks which island runs next by computing a UCB score for every island. Islands that recently produced globally-significant improvements are rewarded with more iterations. Islands that haven't run in a while accumulate a growing exploration bonus that eventually pulls them back into rotation.

When UCB is read and written

READ: end_iteration(), called at the very end of each iteration (after add()) selects current_island for the NEXT iteration WRITE: inside add(), when the archive admits a program (was_added = True, not a migration) only the island that just admitted the program gets its stats updated all other islands are untouched that iteration
Unlike G, UCB rewards decay every time a program is admitted — including non-improvements. When there is no improvement δ_global = 0, so rewards = ρ · rewards + 0 — rewards shrink. An island that keeps admitting programs without improving will see its reward_avg slowly drain to zero, eventually letting the exploration bonus dominate and deprioritising it. G sits frozen without improvements; UCB rewards actively decay.

δ_global — what it is and why it differs from δ

δ_global = min( (combined_score − old_island_best) / (|global_best| + ε), 1.0 ) = 0.0 if no improvement same numerator as δ: how much the new program improved over this island's previous best different denominator: global_best — the best combined_score seen across ALL islands special case: first ever program (global_best = −∞) → δ_global = 1.0 (capped)
Why use global_best and not island_best? UCB rewards need to be comparable across islands. Consider two islands both improving by 0.04:

Island A: was 0.40, now 0.44 → raw_delta = 0.04 Island B: was 0.70, now 0.74 → raw_delta = 0.04 With local normalisation (δ): δ[A] = 0.04 / 0.40 = 0.10 ← looks more productive δ[B] = 0.04 / 0.70 = 0.057 ← looks less productive → island A dominates UCB just for catching up from a low base With global normalisation (δ_global, say global_best = 0.74): δ_global[A] = 0.04 / 0.74 = 0.054 δ_global[B] = 0.04 / 0.74 = 0.054 → same absolute improvement = same reward, regardless of starting level
This is the "poor island bias" fix — without it, a weak island that makes one large relative jump would dominate island selection for many iterations.

Update rules (only for the island that admitted the program)

raw_visits[i] += 1 # always on admission decayed_visits[i] = ρ · decayed_visits[i] + 1.0 # always on admission if improvement: δ_global = Δfitness / (|global_best| + ε) else: δ_global = 0.0 rewards[i] = ρ · rewards[i] + δ_global # always on admission (decays if no improvement) global_best_score updated if new program is a new global best → this shared value makes future δ_global values smaller for everyone

UCB formula — computed for all islands at end_iteration()

Phase 1 — force-explore (raw_visits[i] < min_visits = 3): skip UCB entirely, pick random island from those with < 3 visits ensures every island gets a fair initial sample before UCB takes over Phase 2 — UCB proper (all islands have ≥ 3 visits): reward_avg[i] = rewards[i] / decayed_visits[i] # both numerator and denominator decay at rate ρ # so ratio = recent reward per recent visit (not diluted by old history) exploration_bonus[i] = C · √( ln(N+1) / raw_visits[i] ) # C = 1.41 (√2, hardcoded) N = current iteration number # raw_visits used here (not decayed) — classic UCB exploration guarantee # bonus grows with log(N) but raw_visits only increments for this island # → idle islands accumulate growing bonus, preventing starvation UCB[i] = reward_avg[i] + exploration_bonus[i] next island = argmax UCB[i]

Worked example — 3 islands, iterations 0–10

ρ=0.9, C=1.41, min_visits=3, global_best starts at −∞ ── Iterations 0–8: force-explore phase ────────────────────────────────── Each island gets 3 visits in round-robin order. First program on any island: δ_global = 1.0 (capped, local_best was −∞) After visit 1: rewards = 0.9·0 + 1.0 = 1.00, dec_visits = 1.00 After visit 2: rewards = 0.9·1.0 + 0.0 = 0.90, dec_visits = 1.90 (no improvement) After visit 3: rewards = 0.9·0.9 + 0.0 = 0.81, dec_visits = 2.71 (no improvement) All three islands end up identical: raw_visits=3, dec_visits=2.71, rewards=0.81 reward_avg = 0.81 / 2.71 = 0.299 ── Iteration 9: first real UCB selection (N=9) ─────────────────────────── exploration_bonus = 1.41 · √(ln(10) / 3) = 1.41 · 0.876 = 1.235 UCB[0] = UCB[1] = UCB[2] = 0.299 + 1.235 = 1.534 → random tie-break, say island 1 selected ── Island 1 works, combined_score improves 0.41 → 0.48 ────────────────── δ_global = (0.48 − 0.41) / (0.48 + ε) = 0.146 (global_best updated to 0.48) rewards[1] = 0.9·0.81 + 0.146 = 0.875 dec_visits[1] = 0.9·2.71 + 1 = 3.44 raw_visits[1] = 4 ── Iteration 10: UCB differentiates (N=10) ─────────────────────────────── Island 0: reward_avg = 0.81/2.71 = 0.299, bonus = 1.41·√(ln(11)/3) = 1.261 UCB[0] = 0.299 + 1.261 = 1.560 Island 1: reward_avg = 0.875/3.44 = 0.254, bonus = 1.41·√(ln(11)/4) = 1.091 UCB[1] = 0.254 + 1.091 = 1.345 ← lowest despite just improving Island 2: reward_avg = 0.81/2.71 = 0.299, bonus = 1.41·√(ln(11)/3) = 1.261 UCB[2] = 0.299 + 1.261 = 1.560 → Islands 0 or 2 selected. Island 1 is deprioritised because its raw_visits went up (reducing exploration bonus) faster than its reward_avg rose.
Migration interaction: when a migrant arrives at an island and improves its best, G is updated (intensity shifts toward exploitation) but UCB stats are not touched — the island didn't earn that improvement. raw_visits, dec_visits, and rewards stay unchanged.
1.3 — Mechanism 3: Archive elite_score → admission and eviction

Every island has a UnifiedArchive capped at population_size programs. When a new program arrives and the archive is full, AdaEvolve must decide: does this program displace an existing one? This decision uses an elite score that combines fitness rank and novelty rank (and optionally Pareto rank).

Stage 1: elite_score is purely fitness rank

fitness_percentile(p) = 1 − (fitness_rank(p) / (n − 1)) # rank 0 = best combined_score → fitness_percentile = 1.0 # rank n-1 = worst → fitness_percentile = 0.0 elite_score(p) = fitness_percentile(p) # because fitness_weight = 1.0, novelty_weight = 0.0, pareto_objectives_weight = 0.0

Admission decision

eviction_candidate = most similar non-protected program to the incoming program # similarity = code edit distance (CodeDiversity) # "protected" = top (elite_ratio × n) by elite_score PLUS absolute best by fitness if elite_score(incoming) > elite_score(eviction_candidate): evict candidate, admit incoming else: reject incoming
Intuition: the archive replaces the most structurally similar low-scorer rather than the globally worst program. This preserves programs that occupy unique regions of program space (their "niche") even if they're not top performers. In Stage 1 with novelty_weight=0, this niche protection is mild — the eviction candidate is still chosen by similarity, but the incoming program only wins if its fitness rank is higher.
1.4 — Mechanism 4: Parent sampling — what program the LLM mutates

After the mode is drawn (step 1.1), a parent program is selected from the current island's archive. The selection logic differs per mode and directly determines what code the LLM sees as its starting point.

Exploitation mode: pool = top-25% of archive by combined_score (at least 1 program) parent = random choice from pool Exploration mode: weights_i = novelty_score_i (mean k-NN distance; higher = more isolated in code space) parent = weighted random sample by novelty — fitness is completely ignored Balanced mode: 50% chance → exploitation path 50% chance → exploration path
How novelty_score is computed: for each program p in the archive, compute the average edit distance to its k nearest neighbours (k=5 by default). Programs with lots of unique code structure score high; programs that look similar to many others score low. This is recomputed from scratch whenever the cache is invalidated (every time a program is added or evicted).
1.5 — Mechanism 5: Context program selection — other programs the LLM sees

Beyond the parent, the LLM prompt includes num_context_programs additional programs as examples. These are split into local (from the same island, selected for diversity from the parent) and global (top performers across all islands, selected for quality).

local_count = max(1, floor(num_context_programs × local_context_program_ratio)) = max(1, floor(4 × 0.6)) = 3 global_count = num_context_programs − local_count = 1 Local selection (3 programs): pool = top-50% of island archive by combined_score (quality filter first) from pool, pick the 3 programs MOST different from the parent by code edit distance → diverse but still high-quality context Global selection (1 program): candidates = all programs across all islands (minus parent) return top-1 by combined_score globally → best known solution anywhere serves as an aspirational reference
Why this split matters: local context shows the LLM what diverse approaches already exist on the same island (avoiding re-invention). Global context shows the current best solution anywhere — the LLM can borrow ideas from other islands without waiting for migration. Together they give the model both breadth and a quality target.

1.7 — Optional extension: what changes if Pareto objectives are added

If the evaluator also returns per-difficulty scores (e.g. tight_score, loose_score) and you configure them as Pareto objectives, AdaEvolve adds a multi-objective layer on top of the scalar mechanisms above. Mechanisms 1 and 2 (G and UCB) are unchanged — they always use the scalar combined_score. Mechanisms 3, 4, 5 gain Pareto-awareness.

Config required

pareto_objectives: [tight_score, loose_score] pareto_objectives_weight: 0.3 # weight on Pareto rank in elite_score fitness_weight: 0.5 # weight on combined_score rank novelty_weight: 0.2 # weight on novelty rank (optional) higher_is_better: combined_score: true tight_score: true loose_score: true

What changes in Mechanism 3 — archive elite_score

On every cache refresh, NSGA-II sorting runs across the archive: Dominance: program A dominates B iff A.tight_score ≥ B.tight_score AND A.loose_score ≥ B.loose_score AND at least one is strictly greater → Programs are assigned ranks: rank 0 = non-dominated front, rank 1 = dominated only by rank-0, etc. → Crowding distance computed within each rank (rewards spread-out programs) pareto_pct(p) = 1 − (rank_sorted_position / (n − 1)) # rank-0 programs get highest pareto_pct; rank-0 with large crowding distance best of all elite_score(p) = 0.5 · fitness_pct(combined_score) + 0.2 · novelty_pct + 0.3 · pareto_pct(tight_score, loose_score) Protection rule addition: ALL rank-0 programs are always protected from eviction, regardless of their elite_score.

Effect: a heuristic that scores e.g. combined=0.62, tight=0.55, loose=0.70 and is non-dominated can beat a heuristic scoring combined=0.65, tight=0.50, loose=0.62 (dominated) for an archive slot, because its pareto_pct = 1.0 vs the other's lower pareto_pct outweighs the small combined_score gap.

What changes in Mechanism 4 — parent sampling (exploitation)

Exploitation mode when Pareto is enabled: if Pareto front has ≥ 2 programs: parent = weighted random sample from rank-0 programs, weighted by crowding distance (prefers spread-out front members) else: fall back to top-25% by combined_score (same as Stage 1)

What changes in Mechanism 5 — context program selection (global)

Global context when Pareto is enabled: candidates = global Pareto front (rank-0 across ALL islands) if len(front) ≥ global_count: return front[:global_count] else: return front + top-(global_count - len(front)) by combined_score

What does NOT change

G update → still uses combined_score scalar only UCB rewards → still uses combined_score scalar only Island routing → still UCB on combined_score Best program → reported as Pareto front representative = rank-0 program with highest combined_score
Why add Pareto? Without it, a heuristic that averages 0.65 by being mediocre on tight instances (0.55) but strong on loose (0.75) wins over a heuristic that scores consistently at 0.63 across both. Pareto pressure keeps the consistent heuristic alive and gives the LLM access to both "specialists" and "generalists" as parents and context, potentially allowing the search to synthesise a strong generalist from them.

Cost: adds O(n²) non-dominated sorting per archive update (n ≤ population_size = 20, so negligible), slightly slower convergence on combined_score alone, and requires the evaluator to return the per-difficulty metrics.

2.2 — Adaptive signal: intensity, decay, G search.database

The core of AdaEvolve. Each island has an accumulated signal G that tracks recent improvement history. G drives the search intensity which determines whether the island samples from diversity (explore) or quality (exploit).

G_t = decay · G_{t-1} + (1 - decay) · δ_norm² where δ_norm = min(Δfitness / (|best_score| + ε), 1.0) Δfitness = new fitness − old island best (0 if no improvement) intensity = I_min + (I_max - I_min) / (1 + √(G + ε)) → Low G ⟹ intensity ≈ I_max (explore: island is stagnating) → High G ⟹ intensity ≈ I_min (exploit: island is productive)
Exploration (p = intensity)
Exploitation (p = (1-intensity)·0.7)
Balanced (p = (1-intensity)·0.3)

Example with intensity=0.4: 40% explore · 42% exploit · 18% balanced

2.4 — Archive admission & elite score search.database

2.9 — Paradigm breakthrough search.database

When the global best score barely improves over a window of iterations, a second LLM call (guide_models) is made to generate high-level "breakthrough ideas". These are injected into subsequent prompts as strategic guidance, forcing the search in a new direction.

improvement_rate = (best_score_now - best_score_window_start) / (|best_score_window_start| + ε) stagnating = improvement_rate < paradigm_improvement_threshold AND len(improvement_history) ≥ paradigm_window_size On stagnation: LLM generates paradigm_num_to_generate new ideas. Each idea used paradigm_max_uses times, at most paradigm_max_tried tried. Parent is overridden to global best when paradigm is active.

Note on fitness_weight vs pareto_weight in config.yaml:
The top-level fitness_weight, novelty_weight, pareto_objectives_weight in your config.yaml are fed into AdaEvolveDatabaseConfig at load time and used for the archive elite score. The search.database.fitness_weight in the dataclass default is 1.0 but is overridden by the top-level value from config.yaml when parsed. Check the YAML key paths carefully: top-level keys that match AdaEvolveDatabaseConfig fields are forwarded during from_dict().
